# 분산락을 이용한 선착순 이벤트 구현

## 개요

이 프로젝트는 Redis를 이용하여 분산 환경에서 선착순 이벤트를 안전하게 처리하는 방법을 클린 아키텍처 패턴으로 구현한 예제입니다. 동시에 대량의 요청이 발생했을 때 선착순 처리를 보장하기 위해 다양한 방식의 분산락을 사용했습니다.

## 주요 구현 내용

1. 분산락 인터페이스 및 구현체 (`infrastructure.lock` 패키지)
   - `DistributedLock`: 분산락 인터페이스
   - `RedisSpinLock`: 스핀락 방식으로 구현한 분산락
   - `RedisLuaLock`: Lua 스크립트를 이용한 분산락
   - `RedissonLock`: Redisson 스타일의 워치독 메커니즘이 포함된 분산락

2. 도메인 계층 (`domain.event` 패키지)
   - `Event`: 이벤트 도메인 엔티티
   - `EventParticipation`: 이벤트 참여 기록 엔티티
   - `FirstComeEventDomainService`: 선착순 이벤트 비즈니스 로직

3. 애플리케이션 계층 (`application.event` 패키지)
   - `FirstComeApplicationService`: 선착순 이벤트 유스케이스 구현

4. 인터페이스 계층 (`interfaces.event` 패키지)
   - `FirstComeController`: 선착순 이벤트 API 엔드포인트

## 분산락 구현 방식 비교

### 1. 스핀락(Spin Lock)
- **원리**: 락을 획득할 때까지 반복적으로 시도
- **장점**: 구현이 간단함
- **단점**: 지속적인 재시도로 인한 서버 부하 증가, Redis 서버에 많은 요청 발생

### 2. Lua 스크립트 락
- **원리**: Lua 스크립트를 통해 락 획득/해제를 원자적으로 처리
- **장점**: 원자성이 보장되어 더 안전함, 스핀락보다 부하가 적음
- **단점**: 락 획득 실패 시 재시도 로직이 필요함

### 3. Redisson 스타일 락
- **원리**: 워치독 메커니즘으로 락 타임아웃을 자동 갱신
- **장점**: 긴 작업 실행 중에도 락이 해제되는 문제 방지, 데드락 방지
- **단점**: 구현 복잡성 증가, 워치독 스레드 관리 필요

### 4. Redis INCR 명령어 방식
- **원리**: Redis의 원자적 증가 명령어(INCR)를 이용해 락 없이 카운팅
- **장점**: 락 획득/해제의 오버헤드 없음, 매우 빠른 처리 가능
- **단점**: 복잡한 비즈니스 로직 적용이 어려움, 단순 카운팅에만 적합

## Redis INCR를 이용한 분산락 효과

Redis의 `INCR` 명령어는 원자적인 작업을 보장하므로, 다음과 같은 상황에서 분산락 없이도 동시성을 제어할 수 있습니다:

1. **단순한 카운팅 작업**: 선착순 참가자 수, 재고 차감 등의 단순 카운팅 작업에 적합
2. **속도 우선 시나리오**: 락 획득/해제의 오버헤드 없이 빠른 처리가 필요한 경우
3. **분산 환경의 ID 생성**: 중복 없는 순차 ID 생성 

**코드 예시**:
```java
// 원자적으로 참가자 수 증가 후 최대 수량과 비교
Long currentParticipants = redisTemplate.opsForValue().increment(participantCountKey);
if (currentParticipants <= maxCount) {
    // 참여 성공
    return true;
} else {
    // 초과된 경우 롤백
    redisTemplate.opsForValue().decrement(participantCountKey);
    return false;
}
```

그러나 INCR 방식은 다음과 같은 한계가 있습니다:

1. 복잡한 비즈니스 로직 실행이 어려움
2. 트랜잭션 롤백이 복잡함
3. 작업 실패 시 상태 복구가 어려움
4. Redis 서버 장애 시 데이터 일관성 보장이 어려움

## 클린 아키텍처 장점

클린 아키텍처를 적용함으로써 다음과 같은 이점을 얻었습니다:

1. **명확한 관심사 분리**
   - 도메인 로직, 애플리케이션 로직, 인프라스트럭처 로직이 분리되어 있음
   - 각 계층의 역할이 명확하여 코드 이해가 용이함

2. **의존성 역전 원칙 적용**
   - 도메인 계층이 인프라스트럭처 구현에 의존하지 않음
   - 인터페이스를 통한 의존성 주입으로 유연한 구현체 교체 가능

3. **테스트 용이성**
   - 각 계층을 독립적으로 테스트 가능
   - Mock 객체를 통한 외부 의존성 대체 가능

4. **확장성 및 유지보수성**
   - 새로운 기능 추가 시 기존 코드 변경 최소화
   - 각 계층의 독립적인 변경이 가능

## 선택 가이드

- **단순 카운팅/순서 보장**: INCR 방식 사용
- **짧은 작업/단순 로직**: Lua 스크립트 락 사용
- **복잡한 비즈니스 로직/긴 작업**: Redisson 스타일 락 사용
- **개발 단계/테스트**: 스핀락 사용 (간단하게 구현 가능)
